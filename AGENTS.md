## Workflow

1. **Search first.** Look for existing code before writing new code: the concept name, name patterns (`isValid*`, `format*`, `build*`, `use*`) and literal values. Canonical places: types → `types/`; helpers → `utils/`, `lib/`; constants → `utils/constants.ts`, `config/`; components → `components/ui/`; hooks → `components/hooks/`. Report what you found ("found `isValidCategorySlug` in `utils/url-filters.ts`, will reuse").
2. **Check the data.** Before building a product, SEO or performance idea, or acting on an issue's numbers, check it against live data: GA4 (property `406884331`, Data and Admin APIs; AdSense is linked, so `totalAdRevenue`, `publisherAdImpressions` and `publisherAdClicks` work), Search Console (`sc-domain:esdeveniments.cat`) and CrUX/PageSpeed. Local `gcloud auth application-default` credentials read GA4 and Search Console; the scheduled reports come from `scripts/ga-dashboard.py` (#611) and `scripts/seo-audit.py` (#697). Run `scripts/crux-check.py` by hand; it needs `CRUX_API_KEY` (see `docs/performance/baselines.md`). GA4 traffic is about 80% Chinese bots, so filter rates by country (the dashboard uses Spain). Quote the numbers and date range in the issue or PR. With no credentials (CI agents), say the data wasn't checked instead of guessing numbers.
3. **Plan** in 2–4 steps and wait for confirmation on anything non-trivial.
4. **Implement** with surgical diffs, following the skills.
5. **Verify**: `yarn lint && yarn typecheck && yarn test`, plus `verify-que-fer` for UI or behavior changes.

Stop and propose an alternative when you see a helper used only once, a component with more than 10 props, a file over 200 lines, a function over 100 lines, duplicated logic, or abstractions deeper than 3 levels. Don't create generic utilities without an immediate use. Prefer composition, the standard library and platform APIs (`AbortSignal.any()`, `after()` from `next/server`).

## Hard rules (each one caused an incident)

- **Never read `searchParams` in listing pages** (`app/[locale]/[place]/**`). It makes them dynamic: one cache entry per URL+query ($300+ spike, Dec 2025). Query params (`search`, `distance`, `lat`, `lon`, `price`, `from`, `to`) are handled client-side with SWR; `noindex` for filtered URLs is an `X-Robots-Tag` set in `proxy.ts`.
- **Never add `next: { revalidate, tags }` to `fetchWithHmac` calls in `lib/api/*-external.ts`.** It turns on Next's fetch cache with one entry per URL (146K entries per build, Jan 2026; write-up: `git show ad044ed6^:docs/incidents/2026-01-20-fetch-cache-explosion.md`). External wrappers stay `no-store`; cache with `Cache-Control` in `app/api/*` routes and with `createCache`/`createKeyedCache` (`lib/api/cache.ts`).
- **Server readers call the external wrapper**: our `/api/*` routes don't exist during `next build` (`"<!DOCTYPE"... is not valid JSON`), so `lib/api/*.ts` server readers call the `*-external.ts` wrapper directly, at build and at runtime. The old `isBuildPhase` switch was also true at runtime on Coolify, so the internal-route path never ran in production (see LESSONS.md). A cached reader calls `await connection()` before the cache lookup: a hit skips `fetchWithHmac`'s `connection()`, and a warm cache must not change what Next prerenders.
- **No local barrel files** (`index.ts` re-exports) mixing `"use client"` components from different routes: each re-export lands in the client manifest of every importing route (+24 KB on `/[place]` from a `components/ui/sponsor/index.ts` barrel, since deleted). Import files directly. `optimizePackageImports` only helps npm packages.
- **`cacheComponents` determinism**: a server component that uses `new Date()`/`Date.now()` to decide *what renders* must call `await connection()` first, or run inside `"use cache"` with an explicit `cacheLife` (time is then frozen per entry). Otherwise the replayed tree differs ("Couldn't find all resumable slots") and the page falls back to client rendering. Using dates only for text is fine. The same applies to `generateMetadata` and to helpers that only run on some paths (the listing fallback range, a sitemap year list): read the clock in a cached helper (`buildEventPageMetadata`, `twoWeeksDefaultCached`, `getSitemapYears`), and use `performance.now()` to time things. `next build` never renders these for unknown slugs, so only the dev overlay shows the error (see LESSONS.md). Inside `"use cache"`, get the locale with `rootLocale()` + `setRequestLocale(locale)`; `headers()` is not allowed there. The event page body uses `"use cache"` so it can be stored (ISR); request-time parts (sponsor, news, next edition, promoted events) are passed in as slots.
- **`"use cache"` store**: `cacheMaxMemorySize: 0` (needed for the Redis page cache in `cache-handler.mjs`) also disables Next's built-in `"use cache"` store. `next.config.js` registers `use-cache-handler.mjs` as `cacheHandlers.default` (in-memory LRU, 64 MB per process, lost on deploy). Don't remove it.
- **Sharp** must stay in the Docker image and in `serverExternalPackages`; `/api/image-proxy` depends on it.
- **Raw `fetch()`** can hang forever in containers. Use `fetchWithHmac` (`lib/api/fetch-wrapper.ts`, 10 s timeout) for the backend, `safeFetch`/`fireAndForgetFetch` (`utils/safe-fetch.ts`, 5 s) for other services. ESLint warns on raw `fetch()`; plain `fetch()` to same-origin internal routes (`lib/api/*.ts`, SWR hooks) is allowed.

## API layer

- Server Components → `lib/api/*.ts` readers → `lib/api/*-external.ts` (`fetchWithHmac`, Zod parse, safe fallback). Browser code (SWR) → `app/api/*` routes (`Cache-Control: s-maxage, stale-while-revalidate` per route) → the same wrappers. Never call the backend from pages or the browser.
- Reader caches (details in `api-layer-patterns`): places, categories, regions and cities use a 24 h in-memory `createCache`/`createKeyedCache`; the list caches pass `storeEmpty: false` because their wrappers fall back to `[]`, and `fetchPlaceBySlug` caches a 404 `null` (capped by `maxEntries`). Concurrent misses share one fetch, and a fetch that started before `clear()`/`delete()` doesn't store its result. The categories, regions-with-cities and place-list caches pass `globalKey` (one entry per process, shared by the pages, `proxy.ts`, `/api/revalidate` and `instrumentation.ts`, which Next bundles separately; `/api/categories` and `/api/regions/options` call the wrapper directly and don't read it) and are filled at server start by `warmReferenceCaches` (`lib/api/warm-reference-caches.ts`, capped at 3 s, skipped during `next build`). The `[place]` page reads events through the `"use cache"` reader `fetchEventsCached`; `fetchEvents` and `fetchCategorizedEvents` are uncached (`no-store`). Still through internal routes (`getInternalApiUrl` with `preferConfiguredOrigin`): event and news detail, `news.ts`, `profiles.ts`. `promotions.ts` calls `fetchWithHmac` directly.
- External wrappers: if `NEXT_PUBLIC_API_URL` is missing or the call fails, return a safe empty value (`[]`, `{}`, `null`) for reads; mutations throw. Read exceptions: `fetchPlaceBySlugExternal` returns `null` only on 404 (or a bot-style slug) and throws on other errors or an invalid payload (so callers can tell "not found" from an outage), `fetchEventBySlug` (`events-external.ts`) likewise returns `null` only on 404 and throws with the upstream status (502/504 for a failed request) so an outage never becomes a cached noindexed "not found" page (#750), `fetchPlacesAggregatedExternal` throws when either endpoint fails (a partial list must not be cached as complete), and the authenticated reads in `users-external.ts` rethrow the HTTP status. `searchUsersExternal` returns `null` on failure so `GET /api/users?q=` can answer 502 instead of an empty list. On a non-OK mutation, read `response.text()` before throwing.
- Backend auth: `fetchWithHmac` sends `X-Backend-Key` (`BACKEND_SERVICE_SECRET`; the v2 backend rejects every request without it). While `HMAC_SECRET` is set it also sends legacy `x-hmac`/`x-timestamp` (prod still checks them; remove once prod runs v2). Legacy HMAC signs only `timestamp + pathAndQuery`, so JSON POST/PUT/DELETE pass `skipBodySigning: true`.
- `proxy.ts`/`utils/api-gate.ts` gate most internal `/api/*` routes; public GETs (events, news, categories, places, regions, cities) are allowlisted.
- Mapping: UI `distance` + `lat/lon` → API `radius/lat/lon` via `distanceToRadius` (`types/event.ts`), sent only when set; filter `searchTerm` → API `term`; `byDate` (`avui`, `dema`, `setmana`, `cap-de-setmana`) or explicit `from/to`, not both. Pagination uses `PagedResponseDTO.last`.
- Place page fallback chain: requested place → its region → latest events overall. Keep this order.
- Next's `updateTag`/`revalidateTag` don't reach Cloudflare. A mutation that changes public HTML must also purge its Cloudflare tags (see Hosting and deploys); `/api/revalidate` purges `<host>:html` for places/regions/cities/categories and falls back to purge-everything; with `events` (sent by the admin dashboard after it edits or deletes an event) it expires and purges only those events' pages.
- New endpoint: DTO in `types/api/` → `*-external.ts` → `lib/api/*.ts` reader that calls the wrapper (+ cache) → `app/api/` route only if browser code needs it.

## Filters and URLs

- Canonical URL: `/place(/date)?(/category)?`, omitting `tots`. Filter configs live in `config/filters.ts` and drive the filter chips through `FilterOperations` (`utils/filter-operations.ts`). URL parsing/building and the API mapping are still written per filter; the `filter-system-dev` skill lists every file a new filter touches. `test/filter-system.test.ts` covers the configs.
- Build URLs with `buildFilterUrl`/`buildCanonicalUrlDynamic`; parse with `parseFiltersFromUrl`, `urlToFilterState`, `getRedirectUrl` (`utils/url-filters.ts`). Validate category slugs with `isValidCategorySlug`. Category text in any UI comes from `getCategoryLabel` (`utils/category-helpers.ts`, `Config.Categories` via `CATEGORY_CONFIG`); the SEO `titleSuffix` phrases are for titles and meta only. `distance` is omitted at its default (50).
- `proxy.ts` → `handleCanonicalRedirects` (`utils/middleware-redirects.ts`) 301-redirects legacy `?category=&date=` and `/tots` segments to canonical paths, keeping only the client filter params in `ALLOWED_QUERY_PARAMS`. byDate + `catalunya` + `tots` may redirect home.
- Unknown places get their status in `proxy.ts`, not the page (the static shell, and its 200, is sent before the page's dynamic part runs, so a page `notFound()` serves 200): `checkPlace` (`utils/proxy-place.ts`) → `resolvePlaceForProxy` (`lib/api/places-proxy.ts`) 301s an alias and rewrites a missing place with `status: 404`; it fails open on errors or after 1.5 s. Unknown usernames on `/perfil/<username>(/passats)` get the same 404 rewrite (`isMissingProfilePath`, `utils/proxy-profile.ts` → `isProfileMissingForProxy`, `lib/api/profiles-proxy.ts`): only a backend 404 counts as missing, results are cached 5 min, and the 404 gets `s-maxage=300` so a newly claimed username shows up soon. Unknown category slugs get a 301 the same way (`checkCategory`, same file, reusing `parseFiltersFromUrl`/`getRedirectUrl`). A failed event read can't change its own page's 200 either, so the internal `fetchEventBySlug` (`lib/api/events.ts`) records each 5xx or transport failure by slug (`markEventReadFailed`, `lib/api/event-outage.ts`; a 4xx never counts). Once 3 different slugs have failed within 60 s, `proxy.ts` answers event page documents with a 503, `private, no-store`, `Retry-After: 60` and no `Cache-Tag` (`isEventOutageRequest`, `utils/proxy-event.ts`), so one broken event or bad URL can't 503 the section; the failing requests themselves still go out as 200s. Add every new top-level route folder to `NON_PLACE_FIRST_SEGMENTS` (`utils/middleware-redirects.ts`); a test enforces it.
- News lists (`/noticies`, `/noticies/[place]`) paginate with a 1-based `?page=N` and a fixed `NEWS_PAGE_SIZE`; each page is its own canonical, and a page past the last one is noindexed. `utils/proxy-news.ts` 301s the old 0-based `?page=&size=` and `?cities=` URLs.
- Festa major hubs: `/festes-majors` (calendar), `/festa-major/<place>` (town or region). A town with several festes lists them on its hub, each linking to its part of the programme (`#festa-<key>`); there are no per-festa pages (no search demand, see the research doc). Data comes from events whose title contains "festa major" (`lib/api/festes-majors.ts`, `"use cache"`); grouping, the year pick and the indexing gate live in `utils/festa-major*.ts`. A read cut short by its request cap is kept, reported to Sentry and noindexed on town and region hubs (`complete: false`). The calendar stays indexed (a blip must not drop the main page) and is re-read after 1 h instead of 6 h; the sitemap is cached 5 min instead of 6 h. A town hub is indexed only with `FESTA_MAJOR_MIN_INDEXABLE_ACTS` (5) acts, a region with 2 such towns; `server-festa-major-sitemap.xml` and the region links use the same gate (thin town hubs are `noindex, follow` but still linked from the calendar and event pages). `checkPlace` gives these routes their 404/301 (`catalunya` and a bare `/festa-major` 301 to `/festes-majors`; deeper paths 404; `/<place>/festes-majors` and `/<place>/festa-major` 301 to the hub). A festa major act that ended more than `EXPIRED_EVENT_NOINDEX_DAYS` ago 301s to its town hub (`checkExpiredFestaAct`, `utils/proxy-event.ts`; the backend is asked only for old `festa-major` slugs). New festa major acts add their town hub to IndexNow (`festaMajorHubPathsFor`). Data, URL rationale and the plan for other festivities (Carnaval, Nadal): `docs/growth/festivity-hubs-research-2026-11.md`.
- Next edition: an ended event links, under its title, to the earliest upcoming event in its town with the same `seriesKey` (title minus years, ordinals and Roman numerals; `utils/event-series.ts`). `fetchNextEdition` (`lib/api/event-series.ts`, 6 h keyed cache) searches the title's unchanged part as `term` with no `place` (the backend's `term` is a raw substring match, accents and apostrophes count) and filters the town itself. There is no series URL: a permanent one needs a backend "recurring" flag.
- Festivity pages: `/fires-de-nadal`, `/pessebres-vivents`, `/cavalcades-de-reis`, `/carnaval`, one per entry in `config/festivities.ts` (terms, title regex, `yearOffset`, and its own season: `window(seasonYear)` and `leadDays`. Nadal is 1 Nov–10 Jan; Carnaval is Ash Wednesday − 14 to + 13 days, from `easterSundayYmd` in `utils/date-helpers.ts`). Listings (`PlaceFestesLinks`) and the home "Festes i tradicions" row link the pages in season (from `leadDays` before it) by date only (`inSeasonFestivities`): a festivity read is up to ~180 backend requests on a cold cache and isn't cached when it fails, so pages that render often never wait on one. `lib/api/festivities.ts` reads this season and the last one (`"use cache"`, refreshed hourly in the background; not tagged `events`, since each rebuild is up to ~180 backend requests); the page splits them into upcoming cards, past rows and last season's towns with no date yet, so the year and sections roll over on their own. Indexed with ≥5 towns, even from a capped read (unlike the hubs): the Reis fill 5 January past one page, and esdeveniments-backend#63 keeps that day from ever paging complete. A backend failure keeps the default robots and leaves the page out of the sitemap. A new festivity is a config entry, a route folder and its `Pages.Festivity.types.<key>` text (its slug reaches `NON_PLACE_FIRST_SEGMENTS`, the sitemap and the CDN tags through `FESTIVITY_SLUGS`); the shared text that names the season (`noUpcoming`, `pendingIntro`, `empty`) picks its wording with `{type, select, …}`. Rows show a 56 px `Thumbnail` (`components/ui/common/image/`, image context `thumb`); a town hub's cover is its first act with an image, preloaded with `ImagePreload`.
- Hubs read whole date ranges with `fetchAllEventPagesExternal` (`lib/api/events-external.ts`). `GET /events` with `from`/`to` and no `place` has no stable order (esdeveniments-backend#63), so plain paging repeats and misses events; the helper splits the range into day windows that fit one page, dedupes by id, and reports `complete: false` when it hits its request cap. Don't page date ranges any other way until #63 is fixed.

## Rendering

- Server Components by default; `"use client"` only on the smallest leaf that needs state, effects or browser APIs. Never `next/dynamic` with `ssr: false` inside a Server Component: make a client component and import it.
- Listings are hybrid: the server fetches events, calls `insertAds` once and renders the list (`HybridEventsList`). On the client, `HybridEventsListClient` + `useEvents` (SWR) use the same page size as SSR. Without client filters, it appends only events whose `id` is not already on screen and never inserts ads again; with client filters, it replaces the SSR list.
- Listing map (`components/ui/eventsMap/`): `maplibre-gl`, its CSS and OpenFreeMap tiles load only on the first click (`next/dynamic` in `EventsMapToggle`); its worker is self-hosted at `/static/maplibre-v<version>/` (`scripts/copy-maplibre-worker.mjs` + `setWorkerUrl`). It reads the events on screen from `ListingEventsProvider` (published by `HybridEventsListClient`). Events without a backend `locationPrecision: "VENUE"` coordinate are grouped as a town ring, never drawn as an exact pin (`buildEventMapPoints`, `utils/event-map.ts`); the toggle shows from two map points. The map opens in a full-screen native `<dialog>` (places/events column + map on `lg`, a bottom sheet over the map on mobile), opened by a floating "Mapa" pill on mobile and a "Mapa" chip in the filter row on desktop (`EventsMapChip`; the filter bar is a separate tree, so `EventsMapToggle` registers the opener in `eventsMapLauncher`).
- **Loading UI must be visible.** A page that wraps its whole body in its own `<Suspense>` (the sync `[place]` page; the home page, whose body waits on `connection()`) hides that folder's `loading.tsx`: its fallback is what users see on a first load and on a client navigation. Give it the page skeleton (`components/ui/common/skeletons/`), not only an `sr-only` h1 or `null`; keep crawler-only markup (the `sr-only` h1, the home `HomeStaticFallback`) next to the skeleton. For a dynamic segment with no `generateStaticParams`, a fallback that reads `params` stays out of the generic prerendered shell, so the first flush has a blank `<main>`. Put a static outer `<Suspense>` with the skeleton around the part that reads `params` (the event page's `EventPageGate`), or a `loading.tsx` when it may also wrap the child routes (it can't on `e/[eventId]`, which has `edita/` and `promote/`). Next's instant-navigation validation only checks that a boundary exists, not that it shows anything (`test/place-page-loading-fallback.test.tsx`, `test/home-page-loading-fallback.test.tsx`, `test/event-page-loading-fallback.test.tsx`).
- **Keep the root shell inline.** The root layout has no `<Suspense>`. React moves any finished boundary over ~500 B in the shell into a hidden `<div id="S:…">` and reveals it with `$RC` in a later frame; a root boundary did that to the navbar and the home hero. So everything above a page's own boundary must prerender in every shell, which `next build` enforces (`--debug-prerender` gives stacks):
  - Chrome never reads `usePathname()`/`useParams()` during SSR: they suspend in the generic shell of `[param]` routes. `ActiveLink` wraps each link in its own tiny `<Suspense>` (keep each link's HTML under 500 B or it gets outlined); other pathname readers render only after auth loads or a click (`NavbarLoginLink`, `LanguageMenu`); popups sit in `<Suspense fallback={null}>` in `BaseLayout`.
  - A page or layout that reads request data (`cookies()`, `params` in a generic shell, uncached fetches) has a visible `loading.tsx` or its own boundary below it.
  - Server translations pass the locale: `getTranslations({ locale, namespace })` with `rootLocale()`. A no-locale call can resolve next-intl's shared config from `headers()` and block the root provider.
  - Root providers (in `app/[locale]/layout.tsx`) never change their context value after hydration. They hydrate before the page's streamed boundaries are revealed, and a context change makes React drop those boundaries' server HTML and client-render them (the `/preferits` empty state showed twice). Changing state goes through `createExternalStore`/`useExternalStore` (`lib/context/external-store.ts`), as in `AuthProvider` and `AdProvider`; `startTransition` doesn't help.
  - Form inputs that render before hydration are disabled until then (`EventForm`'s `<fieldset disabled={!isHydrated}>`), or typing and clicks are lost.
- `partialPrefetching` is on: links prefetch a route's shared shell. Never set `prefetch={true}` on a `<Link>`; `PressableAnchor` (`components/ui/primitives/`) defaults to `false`.
- Hooks: `useRef` for flags that don't affect rendering (analytics sent, effect ran); memoize only what profiling shows.
- News: `app/[locale]/noticies/` (all news), `noticies/[place]` (news for a place), `noticies/[place]/[article]` (one article).

## Performance (measured; see `docs/performance/baselines.md`)

- **Google scripts load at three different times.** Funding Choices (consent box) is a plain `<script async>` in the `<head>` of `app/[locale]/layout.tsx`, next to the `googlefcPresent` iframe script. Never move it into a Next `<Script>`: it then waits for hydration and on a first visit the consent box becomes the LCP (~5 s on a slow phone). `armConsentFallback` (`app/GoogleScripts.tsx`) covers pages where FC shows no box. AdSense (`app/GoogleScriptsHeavy.tsx`) loads only after consent, on the first tap/key/scroll or 4.5 s after load (`onFirstInteractionOrTimeout`, `utils/browser.ts`). GA and other analytics use `<Script strategy="lazyOnload">`.
- **Images**: external images go through `/api/image-proxy` (Sharp) and render as `<picture>` via `ImageServer`/`ClientImage` (`components/ui/common/image/`), not `next/image`. Build URLs with `buildResponsivePictureSourceUrls` (`utils/image-cache.ts`). Quality is 50 everywhere (`getOptimalImageQuality`); allowed values are `images.qualities` in `next.config.js`. Retries: `useImageRetry`.
- **One LCP image per page** gets `priority` (eager, `fetchPriority="high"`) plus a matching `<link rel="preload" as="image" imageSrcSet>` built with the same helper, widths and quality (see `PlacePageShell.tsx`, `app/[locale]/e/[eventId]/page.tsx`). On listings it is the first card with an image (`hasCardImage`, `utils/event-helpers.ts`). The home hero is a static AVIF/WebP set in `config/hero-image.ts`.
- **Icons repeated on every card** (map pin, hearts) come from the sprite in `components/ui/common/IconSprite.tsx`: `<svg><use href={`#${SPRITE_ICON.mapPin}`} /></svg>`.
- **No size floor on an ad's ancestors.** Once an ad loads, AdSense sets `height: auto; min-height: 0` (inline, `!important`) on every ancestor of it except `html`/`body`, `<main>` included. A `min-h-*` there stops working, and the footer jumped on client navigations (0.24 CLS each). Put floors on elements that never contain an ad, like the zero-width strut next to `<main>` in `BaseLayout`. Move fixed bars with `translate-*`, not `top` (every frame of a `top` transition is a layout shift). See LESSONS.md.
- **No 300 ms reveal throttle.** React 19.2 holds each streamed boundary until 300 ms after the shell's first frame. `REVEAL_THROTTLE_OFF_SCRIPT` (`utils/constants.ts`), the first inline script in the root `<head>`, turns that off in visible tabs (LCP −170 to −250 ms on listings, events and `/preferits`, same CLS and TBT; hidden tabs keep React's timeout, since they run no animation frames). Keep it before React's scripts. `test/react-reveal-throttle.test.ts` fails if a React upgrade changes how `$RT` is read; then remeasure before you adapt or drop it.
- **i18n payload**: client components receive only the namespaces in `lib/i18n/client-namespaces.ts`. Messages are precompiled: plain ICU strings, no `t.raw()`, lists in `i18n/locale-lists.json`.

## Security

- CSP lives in `utils/proxy-csp.ts` (applied to pages by `proxy.ts`): host allowlist with `'unsafe-inline'` (keeps pages cacheable for ISR/PPR); no nonces. Add new script/connect hosts there. The other security headers are in `next.config.js` `headers()`.
- JSON-LD is rendered server-side by `components/partials/JsonLdServer.tsx`, which escapes `<`. Use `toLocalizedUrl(path, locale)` (`utils/i18n-seo.ts`) for its URLs and `generateBreadcrumbList()` (`components/partials/seo-meta.ts`) for breadcrumbs.
- Errors: pass the original error to `captureException(error)`. Wrap `new URL()` in try/catch inside error handlers.

## i18n

- Locales in `i18n/routing.ts` (`as-needed` prefix). Use `Link`, `redirect`, `useRouter`, `usePathname`, `getPathname` from `@i18n/routing`, never `next/link` (ESLint warns).
- Server: `getTranslations` (`next-intl/server`); client: `useTranslations`/`useLocale`. Never pass messages down manually. Text lives in `messages/{ca,es,en}.json`; reuse keys.
- `proxy.ts` sets `x-next-intl-locale`; don't write your own locale detection. Vitest aliases `next-intl` to `test/mocks/next-intl*.ts`.

## Types

- No `any`; use `unknown` and narrow. Type aliases and interfaces live in `types/` (ESLint enforces it in `app/`, `components/`, `lib/`, `utils/`; a few config-only types stay in `config/`): DTOs in `types/api/`, shared UI types and props in `types/common.ts`/`types/props.ts`. Define each type once and import it; see `types/README.md` for where each kind goes.

## UI

- Read `DESIGN.md` and the `design-system-conventions` skill. Semantic classes (`heading-*`, `body-*`, `btn-*`, `card-*`, `badge-*`, `flex-center`, `stack`) and tokens (`text-foreground`, `text-muted-foreground`, `bg-muted`, `border-border`, …). Never `gray-*`, hex colors or the removed aliases (`primarydark`, `whiteCorp`, …). Components: `Button` and `Badge` in `components/ui/common/`.
- Dates in UI: `getFormattedDate(start, end)` from `utils/date-helpers.ts`, not `toLocaleDateString`.
- Whether an event has started or ended comes from `computeTemporalStatus` (`utils/event-status.ts`; `hasEventEnded` in `utils/event-window.ts` when client code needs only past or not, without the status labels), and its start and end from `resolveEventWindow` (`utils/event-window.ts`), all in Madrid time. Never compare `new Date(event.endDate)` with now or parse event times by hand: the server runs in UTC, so a hand-rolled check drifts by hours. New edge cases go in `test/event-status-matrix.test.ts`, which runs under four time zones (LESSONS.md › Event start and end come from one place).

## Hosting and deploys

- Docker on Hetzner via Coolify, behind Cloudflare (DNS, edge cache, TLS). Redis holds the Next page cache. `develop` deploys to staging; `main` is production. Infra limits: `docs/self-hosted-resource-limits.md`.
- Cloudflare caches public HTML on www for `s-maxage=1800` (not `/api/*`, RSC or `Accept: text/markdown` requests, staging or AI bots; each exclusion is a Bypass Cache Rule ordered below the HTML rule, see `docs/incidents/2026-04-04-cloudflare-rsc-cache-poisoning.md`). `applyPageHeaders` (`utils/proxy-page-headers.ts`, called from `proxy.ts`) labels each CDN-cacheable page with a `Cache-Tag` (`<host>:html` plus `home`, `place:<slug>`, `event:<slug>` or `user:<username>`, built in `lib/cdn/cache-tags.ts`; never on `private, no-store` responses). Publish, edit and delete purge the event's tags in `after()` through `purgeEventPagesFromCdn` (`lib/cdn/cloudflare-purge.ts`). Keep the long `s-maxage`; purge instead of shortening it. Free plan: 5 purge requests/min, 100 tags each, so send one batched request per change. Needs `CLOUDFLARE_ZONE_ID` and `CLOUDFLARE_API_TOKEN` (Cache Purge) at runtime in Coolify; `/api/health` reports `cloudflarePurgeConfigured`.
- Every deploy waits in "Wait for Coolify deployment to complete" until the old container has left the pool (10 health checks in a row on the new commit). Production then purges Cloudflare, checks every referenced `/_next/static` asset with `scripts/check-static-assets.sh` and purges once more if one fails; the smoke tests run the same check on staging. Never purge or asset-check before that wait: during the rollover the old container re-caches old HTML and 404 chunks (`docs/incidents/2026-11-08-cloudflare-cached-chunk-404.md`).
- After that purge, `submitEventsToIndexNow` (`lib/seo/indexnow.ts`) pings IndexNow (Bing, Yandex, …) with the event's ca/es/en URLs, on the production site only. The key is `INDEXNOW_KEY` (`utils/constants.ts`), served as `public/<key>.txt` and excluded from the `proxy.ts` matcher; change both together.
- Server Action IDs are salted with `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` at build time (GitHub secret per Environment, Docker secret mount; the deploy fails without it), so pages already open keep working across deploys. Don't set it in Coolify, and don't rotate it casually: a new key breaks every open page once (see LESSONS.md).
- Rollback: Coolify → Deployments → Rollback, or GitHub Actions "Deploy to Coolify" with `skip_ci`. It does not undo backend or DB changes.
- Release `develop` → `main` at least weekly. From Aug 2 to Nov 4, 2026 nothing shipped to production; Googlebot got 5xx and slow answers from Aug 18 until that release (#752), and the fixes sat in `develop`. Small releases also make a regression easy to trace to one change.
- `uptime.yml` (every 15 min) checks the cached homepage, the image proxy and one random event page from the sitemap (200 within 10 s, with Event JSON-LD), since event pages usually miss the Cloudflare cache and show origin trouble the homepage hides.
- Coolify PR previews may lack runtime secrets, so they serve an empty `<main>`. Don't use them for SEO/SSR checks unless `curl -sS https://pr-XXX.esdeveniments.cat/ | grep -c '<h1'` is above 0 (`docs/incidents/2026-04-23-coolify-pr-preview-empty-html.md`).

## Conventions

- Components PascalCase, hooks `useXxx`, helpers lowerCamelCase, 2-space indent, path aliases.
- Constants in `utils/constants.ts`; config over conditionals; no duplicated literals.
- Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`). Short-lived `feat/*`/`fix/*` branches into `develop`. PRs follow `.github/PULL_REQUEST_TEMPLATE.md` (summary, screenshots for UI, test plan).
- Never commit secrets or env files; never edit build output (`public/sw.js`, `public/robots.txt`, `.next/`).
